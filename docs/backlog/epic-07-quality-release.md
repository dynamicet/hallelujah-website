# Epic 07 — Quality, Security, Release, and Operations

**Outcome:** A release candidate proven safe, accessible, resilient, performant, operable, recoverable, and content-correct in the approved environments, followed by an approval-controlled launch and stabilization period.  
**Priority:** P0/P1  
**Milestones:** Continuous through M1–M5; release M6–M7  
**Primary owners:** QA/Accessibility Lead, Security Lead, Delivery Lead, Product Owner, Content/Language owners, Operations

## Defect policy

| Severity | Example | Release rule |
| --- | --- | --- |
| `S1 Critical` | Wrong emergency route, personal-data disclosure, exploitable compromise, data loss, sitewide outage | Stop/revert; no launch or continued exposure |
| `S2 High` | Critical journey blocked, appointment duplication/unknown state mishandled, major AT barrier, false clinical/operational claim | Must fix and retest before affected release |
| `S3 Medium` | Recoverable noncritical defect, isolated responsive/content issue | Fix before release or accept with owner, mitigation, and near-term expiry |
| `S4 Low` | Cosmetic issue with no task, meaning, safety, or accessibility effect | May enter measured post-launch backlog |

## Epic exit criteria

- Every Must requirement and formal release gate has current evidence against the exact release candidate.
- Human testing closes the prototype evidence gaps; automated screenshots are not used as substitutes.
- Security, deployment rollback, database restore, incident, and wrong-content correction procedures are rehearsed.
- Production launch and continued operation have named authority and measurable escalation paths.

## Explicit exclusions

- No release based only on CI green status, visual screenshots, Lighthouse score, or prototype QA.
- No permanent risk exception without expiry and retest.
- No production deployment from an unreviewed workstation build.
