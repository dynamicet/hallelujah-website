PUBLIC PAGE AUDIT — 19 NOVEMBER 2026

Scope and verdict

The shared public layout is coherent: pages inherit one header, main landmark,
skip link and footer. The intentional full homepage / compact interior footer
variants are appropriate and should stay. About Us, directories, patient guides
and editorial pages can retain different compositions within that shared shell.
Implementation integrity needs work in workflow messaging and style ownership;
the layout itself does not need replacement.

P1 — Appointment simulation looks like an operational request workflow

Location: apps/web/src/app/(public)/appointment/page.tsx:36
          apps/web/src/design-system/templates/appointment-template.tsx:158

Category: implementation integrity / workflow clarity.
Evidence: localSimulation is enabled. The opening hides the unavailable-form
notice; subsequent steps request name, telephone and permission to contact the
visitor. Completion displays "Request complete" and reference HH-1042, with
instructions to contact the hospital to confirm a time. Nothing is sent by the
local simulation. Fresh complete-390.png confirms that presentation. The browser

Impact: a visitor can mistake a rehearsal for a request received by the hospital.
Recommendation: explain the preview before data entry; request sample details;
label its completion/reference as examples and state that nothing was sent.
Update the test to protect truthful messaging while retaining the tested flow.
Suggested follow-up: Impeccable clarify, then harden.

P2 — Public styling reaches into CSS Module implementation names

Location: apps/web/src/app/care-pages.css:11, :23, :35
Category: implementation integrity / maintainability.
Evidence: global rules match substrings such as [class*='introductionCopy'],
[class*='cardContent'], [class*='primaryLink'] and [class*='contentLayout'].
Impact: a private class rename can silently remove public styling. Future
components inherit the shared shell, but cannot reliably inherit these body
styles merely by following a documented component API.
Recommendation: move ownership into component styles and explicit variants, or
use stable, documented data attributes where a website skin is required. Migrate
incrementally and preserve the intended custom layouts.
Suggested follow-up: Impeccable harden.

P2 — Editorial cards assume a heading level that fails in the archive

Location: apps/web/src/website/news-resources.tsx:16
          apps/web/src/app/(public)/news-resources/page.tsx:30
Category: accessibility / semantics.
Evidence: EditorialCard always renders h3. On the homepage its parent section
has h2, which is appropriate. The archive renders those same cards directly
under its h1, producing h1 -> h3. Verified in the rendered heading inventory.
Impact: heading navigation represents the archive structure less clearly.
Recommendation: let the card accept a restricted heading-level option; use h2
in the archive and h3 under the homepage section. Preserve visual typography.
A skipped level alone is not asserted here as a WCAG failure.
Suggested follow-up: Impeccable harden.

P2 — Preparation-guide action links bypass the shared action treatment

Location: apps/web/src/app/(public)/services/[slug]/page.tsx:44–48
          apps/web/src/app/website.css:53
Category: responsive design / component consistency.
Evidence: the preparation-guide branch uses bare standalone Links for the visit
checklist, all services and help choosing care. Comparable service-page actions
use text-link, including a 44px minimum height and a defined hover treatment.
The narrow DOM inventory reports 21px-high boxes for those bare guide actions;
their mobile screenshot confirms the different presentation.
Impact: equivalent next actions receive different feedback and hit areas.
Recommendation: share a text-action component/pattern for standalone next steps;
retain normal inline links within sentences. Do not force every content link to
look like a button. Existing global focus styling still applies.
These measurements are not a WCAG target-size failure: spacing/inline exceptions
must be evaluated before claiming one.
Suggested follow-up: Impeccable adapt / polish.
